     New file: backend/app/utils/async_tasks.py

     Both enrich_on_tracking_start (1B) and seed_on_trip_creation (1C) need the
     same pattern: spawn an async task with a fresh DB session, log all failures
      (including RuntimeError when no event loop exists). Extract once:
     import asyncio
     import logging
     from app.database import SessionLocal

     logger = logging.getLogger(__name__)

     def spawn_best_effort(coro_factory, *args, label: str = "background_task"):
         """Fire-and-forget an async task with a fresh DB session.
         
         coro_factory: async callable that takes (db_session, *args)
         """
         async def _run():
             local_db = SessionLocal()
             try:
                 await coro_factory(local_db, *args)
             except Exception:
                 logger.warning("%s failed", label, exc_info=True)
             finally:
                 local_db.close()
         try:
             asyncio.get_running_loop().create_task(_run())
         except RuntimeError:
             logger.warning("%s skipped: no running event loop", label)
     Key: RuntimeError is logged, not silently swallowed.

❯ and should i also run the worker functions right with the fastapi server?     
● Yes — the FastAPI server alone only handles API requests. The advisory
  pipeline needs three workers polling in the background:

  1. advisory_worker — picks up queued jobs, runs the 7-stage pipeline (scrape,
  rank, deliver)
  2. advisory_cycle_worker — polls trip_advisory_state every 30s, fires
  location_trigger jobs for active trips
  3. advisory_ignore_sweep_worker — polls every 10min, expires unacted
  advisories, pauses brain after 3 ignores

  For local testing, run them in separate terminals alongside the server:

  # Terminal 1: API server
  cd backend && ./venv/Scripts/python.exe -m uvicorn app.main:app --reload

  # Terminal 2: advisory job processor
  cd backend && ./venv/Scripts/python.exe -m app.workers.advisory_worker

  # Terminal 3: cycle worker (triggers advisory jobs during live trips)
  cd backend && ./venv/Scripts/python.exe -m app.workers.advisory_cycle_worker

  # Terminal 4 (optional): ignore sweep
  cd backend && ./venv/Scripts/python.exe -m
  app.workers.advisory_ignore_sweep_worker

  The cycle worker is the critical one — without it, starting a live session
  seeds the brain and sets it to active, but no location_trigger jobs get
  created. The ignore sweep is less urgent for testing.

  For the flow to work end-to-end you also need OPENROUTER_API_KEY set in
  backend/.env (for Reddit scrape + LLM extraction). BRIGHTDATA_WS_ENDPOINT is
  optional — GMaps stage skips gracefully without it.

❯ how can we host headed browser on ec2?                                        

● You can't have a real display on EC2, but you don't need one. Xvfb (X Virtual
  Framebuffer) creates a fake display in memory. The browser runs in "headed"
  mode (no --headless flag) but renders to a virtual screen. Google can't tell
  the difference.

  # Install on EC2 (Ubuntu/Debian)
  sudo apt install xvfb

  # Run any script with a virtual display
  xvfb-run python -m app.workers.advisory_worker

  That's it. The browser thinks it has a monitor. Google sees a normal headed
  browser. Persistent profile still works, cookies accumulate, reviews render.

  For debugging you can add VNC on top of Xvfb to actually see the browser
  remotely, but that's optional — Xvfb alone is enough for production.
